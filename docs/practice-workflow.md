# Developer context and deliberate practice

Preferences contains an optional developer profile (name, existing experience selector, suggested/custom languages and stack, background), up to ten projects, and collapsible practice context. Names are used for profile presentation. Explicit challenge requests take precedence over saved preferences. Recent-challenge sharing stays off by default.

Known technology aliases normalize to catalog IDs; custom names survive storage and display. Projects have a name (120 characters), at most 20 technologies (80 characters each), and a contribution (600 characters). Languages and stack each support up to 50 entries. The existing background limit is 4,000 characters. Partial/older preference writes preserve omitted fields; explicit null/empty arrays clear them.

`developer_context_updated_at` is nullable and server-controlled. Only changed developer/practice information advances it. Model choices, history-sharing settings, unchanged saves, previews, draft application, and cancelled imports do not. Historical timestamps remain null. The column uses a Bun-compatible timestamp mapper to preserve UTC and milliseconds.

Preparation and generation use one context projection: experience, preferred languages/stack, concise professional background, goals, known concepts, relevant topic familiarity, and up to three related projects. Matching normalizes request terms and technology aliases; ties preserve project order and unrelated projects are omitted. Identity fields, contact details, and resume source are excluded. `developerContext.updatedAt` is ISO UTC or null. Successful challenges freeze this exact projected context, including the timestamp. Later preference edits do not alter existing challenges. Missing legacy context is never reconstructed from current preferences.

## Resume import

`POST /profiles/resume/preview` requires the active `X-Profile-Id`. Send multipart `file` (PDF/DOCX) or JSON `{ "text": "..." }`. The response is `{ data: { draft, warnings } }`; it does not save preferences. `draft` contains only `displayName`, `aboutMe`, `languages`, `stack`, and projects with `name`, `technologies`, and `contribution`.

The upload limit is 10 MiB; PDFs have a 30-page limit. Extracted/pasted text must contain 40–100,000 characters. These limits apply only to resume import, never source-code uploads. A cancellable worker runs [unpdf](https://github.com/unjs/unpdf) text extraction or [Mammoth's raw-text API](https://github.com/mwilliamson/mammoth.js#api) with a 20-second parsing deadline, and is terminated on every exit path. Documents are never rendered as HTML or retained. Malformed/encrypted documents and scanned PDFs return specific errors with pasted text as the fallback. OCR is outside this version.

One structured extraction call uses the configured model gateway. Every suggested value must match its supporting excerpt, and each excerpt must appear in the extracted source after canonical Unicode and whitespace normalization. This tolerates document line wrapping and spacing while preserving words, case, and punctuation; it does not accept paraphrases or invented claims. Alias normalization happens after evidence validation. Resume instructions are treated as data. The extractor does not infer experience level, years of experience, mastery, goals, or familiarity. It excludes career/location/compensation/job-search preferences.

Extracted text is sent to the configured AI provider and can appear in existing AI logs under `resume_import`. Logs follow the same profile scoping, credential redaction, retention, and cancellation policy as other AI operations. The binary is not retained.

The dialog supports choose input, extracting, and editable draft review. Only currently empty fields are selected initially. Selected scalar fields replace unsaved values; selected collections merge while preserving existing entries and removing exact/alias duplicates. The ten-project and fifty-technology limits preserve existing entries first. Applying updates the form; **Save preferences** persists it. Errors, cancellation, and closing the dialog do not save anything.

## Generation and review contracts

Future challenges use prompt `practice-v3.1`, contract version `2`, and calibration `difficulty-bands-v1`. The structured result has `status`, nullable `challenge`, nullable `question`, and `options`. Ready requires a challenge and no question/options. Essential clarification requires a question, no challenge, and zero options for free text or two to three distinct alternatives.

Successful creation remains HTTP 201. Essential clarification is HTTP 409 with `CHALLENGE_NEEDS_CLARIFICATION` and `error.details: { question, options }`. Send ordered `clarificationHistory` entries containing `question` and `answer`; the original `clarificationContext` single-answer field remains accepted. Each answer starts a fresh bounded generation attempt. Preparation only checks for missing requirements; it never assigns coding work. Assignments placed in a clarification field are rejected in both preparation and generation, rather than shown as questions or saved as challenges. The UI has no Skip action for essential questions. The local server also retains a bounded pending-question guard for active requests; generation independently checks whether requirements are sufficient, including after a restart or preparation transport failure.

Models estimate a band, never a number. A mismatch receives one corrective request to revise actual reasoning demand. A second mismatch returns retryable `MODEL_DIFFICULTY_MISMATCH` and saves nothing. Other failures receive no automatic regeneration. New numeric difficulty values are null. Existing numeric columns, historical values, requirements, snapshots, reviews, and scores stay unchanged.

New assignments use one authoritative `completionCriteria` checklist. Both model schemas and runtime validation require empty `constraints` and `implementationMilestones`. Scope-specific criterion/character limits remain; suggested word counts are guidance, never a rejection gate. Legacy arrays remain readable and rendered. Stable criterion IDs remain in structured review mappings and diagnostics while ordinary assignment/review presentation uses readable requirement text.

Direct, Codex, and compatibility reviews share the frozen-requirement policy. Verification is independent, mapped, and read-only. Invalid generated expectations and environment failures are limitations, not automatic defects. Acceptance requires all mandatory criteria met with no required findings, outstanding question, or mandatory next step. Revision requires a mapped unmet criterion and finding; essential uncertainty requires `needs_evidence`. The 4 + 3 + 3 rubric retains nullable dimensions and server-calculated totals. Acceptance does not mark a challenge completed.

Quiz-specific instructions, answer explanations, schemas, autosave, and recovery remain separate from challenge instructions and resume extraction.

## Validation and rollout

Run `bun run test:isolated` to start a disposable PostgreSQL 17 container on an ephemeral localhost port, run the suite, and remove the container. No production database is used and no ordinary test makes paid model calls. `TEST_DATABASE_URL` can also point a direct `bun test` run at a separately provisioned test database. The backend reuses its SQL client across Bun hot reloads to avoid accumulating development connection pools. The suite verifies that twenty module reloads reuse a database connection. It also rehearses the additive migration against populated historical records and exercises real PDF/DOCX fixtures, worker timeouts/cancellation, profile isolation, generation branches, calibration, review validation, quizzes, and submission uploads.

Run `bun run check` and `bun run build`. `bun run prompt:eval` lists representative scope/difficulty cases without making requests. Explicit `bun run prompt:eval --run` makes paid calls through the configured provider, using the separate `prompt-evaluations@grill-me.local` local profile. It saves generations, hints, and synthetic review fixtures in that profile and writes a JSON report under `EVALUATION_ROOT` (or the existing evaluations directory). Inspect topic fidelity, directness/readability, solution leakage, calibration, equivalent implementations, missing evidence, and review fairness. Word counts are informational.

Apply migration `0005_bored_zodiak.sql` and roll out backend/frontend together. The migration only adds nullable `developer_context_updated_at`, with no backfill or JSON rewrite. Rehearse against an isolated populated database before production rollout. Back up the installation normally; do not regenerate old challenges or recompute scores. Existing local profiles and model configuration are retained. No document archive, embedding service, new account layer, or career features are introduced.
